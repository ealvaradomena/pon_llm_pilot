Methods

Boundary-object coding under the preserved 2024 protocol

Study objective

The computational pilot examines whether a large language model can extract governance features from textual boundary objects associated with purpose-oriented networks (PONs). Each boundary object is presented as a document-level input, and the model returns one binary classification for each governance question.

The contemporary extension implemented in this repository asks a single comparative question: how does a new model perform when the 2024 protocol is held fixed? The model is therefore the intended treatment; the instrument and prompting design are not modernized.

Cases and source documents

The recovered source corpus contains six PONs.

The source texts are stored locally in input/boundary_objects/, eliminating the original runtime dependency on a Google Drive directory while preserving the supplied documents.

Binary coding instrument

The computational workflow contains 15 ordered yes/no questions.

Note

The manuscript later reports 14 prompts. The preserved computational instrument contains one additional working-groups item. It is retained here because the new-model exercise reproduces the historical computational protocol rather than revising it retrospectively.

Recovered 2024 API protocol

The final Dec. 24 Quarto implementation used the OpenAI Python client and Chat Completions. The request supplied only model and messages explicitly. The requested model alias was gpt-4-turbo.

The messages were constructed as follows:

  1. System message — the policy-analyst instruction followed by the ordered questions.
  2. User message — the complete boundary-object text.

No explicit values were supplied for temperature, top-p, token limit, seed, structured response format, or tools. Consequently, those values were whatever defaults applied to the service at the time and should not be reconstructed retroactively.

The preserved policy-analyst instruction is:

You are a policy analyst focused on extracting organizational features from documents that regulate the organization and functioning of specific organizations. I will provide the documents and a list of yes-no questions. You will only return TRUE or FALSE responses according to the list of yes-no questions, including a row with the question itself. The output must be in CSV format.

The historical code then concatenated The questions are: and the question list directly to this string. The new runner intentionally preserves that exact string construction rather than cleaning its whitespace.

Prompting conditions

Two conditions are retained:

  1. Zero-shot — the baseline instruction and questions, with no examples.
  2. Step by step — the literal phrase Let's think step by step appended before the question list.

The contemporary runner does not introduce a schema, examples, revised role prompt, or other prompt engineering. Only the requested model ID changes.

BEREC provenance caveat

BEREC was part of the six-PON source corpus and was heavily used while the pipeline was being developed. Its preserved binary output, BO1A-2024-12-23-55_cat.txt, is retained in output/.

That file predates the Dec. 24 final run. Earlier Quarto versions around the BEREC development stage show a different message-role layout, with the boundary-object text used as the system message and the question prompt used as the user message. The surviving materials do not establish with sufficient certainty which exact code state produced the Dec. 23 BEREC file.

Accordingly, current runs include BEREC under the final manuscript-facing protocol, but BEREC is excluded from statistics explicitly labeled as a strict same-protocol legacy comparison. Its legacy/current differences remain available descriptively.

Legacy human-reference evaluation

The recovered Dec. 24 analysis compares each model output with one human-reference vector per organization for IRG, EU Health Coalition, cOAlition S, CAN, and CEER. Those labels are stored in input/reference/legacy_human_responses.csv.

They are the single reference vectors used by the recovered computational code. They should not be conflated with the later three-human-coder validation described in the manuscript.

New-model provenance

Every new request stores the raw model output without normalization, plus a JSON sidecar containing the requested and returned model IDs, completion ID, UTC request time, prompt and input hashes, usage data, system fingerprint when available, selected HTTP headers, and the list of parameters that were deliberately left unspecified.

These additional records improve provenance without altering what is sent to the model.
